# 开发 Agent 工作流（DEV_WORKFLOW）

> 适用项目：agent-harness
> 需求输入：用户当轮指令 + `docs/需求分析.md`（功能清单、测试要求、提交物）+ `docs/架构设计题.md`（架构取舍参考）
> 本文件用于指导「开发 Agent」执行功能开发任务。

## 全局纪律（必须遵守）

1. **Git 先提交不推送**：所有工作完成后只 `git commit`（本地提交），一律不 `push`；是否推送由用户决定。
2. **审查**：任务结束前先自审一遍，再交付结果。
3. **日志**：每次重要 Bug 修复后，撰写一份 devlog（见第 7 步）。
4. **严谨**：绝不伪造内容；知识盲区明确说不，或先检索权威来源补全；不确定的结论标注口径与来源。

## 工作流

### 1. 需求探查与澄清
- 动手前完整读取：用户需求指令、`docs/需求分析.md`、`docs/架构设计题.md`；不跳读、不凭印象、不用二手摘要代替。
- 核实版本、名词、接口与调用方式；关键歧义若会改变实现方向，先提问澄清，不猜测。
- 需求或设计需要深度打磨时，引导用户运行 `/grilling`（grill-me）会话。
- 开工前确认：交付物、验收标准、功能边界、本次改动范围。

### 2. 实现设计
- 拆解功能点，每个功能明确四类边界：
  - 正常路径（主流程）
  - 异常路径（错误输入、失败处理）
  - 边界值（空、极值、临界、超长、类型不符）
  - 业务特殊场景（并发、重复调用、会话隔离、数据一致性等）
- 只改被点名的范围，保留未要求改动的内容；个人判断另行标注。

### 3. 实现功能
- 小步实现：一个功能一个功能做，每个功能形成独立可提交单元。
- 复用项目已有结构；写入安全实现（防注入、防越权、超时与异常兜底）。

### 4. 边界分析与功能测试（核心环节）
- 每实现一个功能，**立即生成对应的功能测试**，用例必须覆盖多方位（至少包含第 2 步的四类边界）。
- 对照 `docs/需求分析.md` 的测试清单逐项落地：工具调用、会话、压缩、异常处理、轮次、集成等。
- 运行测试，**全部通过后才允许提交**；失败则修复并重跑，直到通过。

### 5. 验证
- 用与生成路径不同的方式回读/运行，检查用户真正看到的层（真实入口、渲染结果、关键数据重算）。
- 自查清单：输入已读全、约束未越界、事实可追溯、关键动作已执行。

### 6. 版本管理 & 提交
- 每个功能一个独立提交；提交信息格式：`<功能名>：<一句话摘要>`，可附测试结果。
- 只 `git commit`，不 `push`；推送由用户决定。
- 用 `git commit <文件路径>` 限定提交范围，不把用户/他人未要求提交的暂存改动混入自己的提交。

### 7. devlog（问题解决报告）
- 每次重要 Bug 修复后必须撰写 devlog，记录：问题现象、根因、修复方案、验证结果。
- 存放目录：`docs/devlog/`（不存在则先创建）。
- 命名格式：`MM-DD HH：mm-具体解决的问题.md`
  - 示例：`11-04 14：30-修复上下文压缩丢失会话.md`
  - 注意：时间冒号使用**全角** `：`（Windows 文件名不允许半角 `:`）。

## 项目提交物提醒
- 最终提交内容以 `docs/需求分析.md` 底部清单为准：API、连接、README（运行方式、系统设计、memory 召回时机与放置方式说明）、AI Prompt 与解决记录。
- README 与功能详解文档的维护由「文档撰写 Agent」负责（见 `DOCS_WORKFLOW.md`）。
