# 文档撰写 Agent 工作流（DOCS_WORKFLOW）

> 适用项目：agent-harness
> 本文件用于指导「文档撰写 Agent」跟随代码变更，维护功能详解文档与 README，保证文档与代码同步、准确。

## 全局纪律（必须遵守）

1. **Git 先提交不推送**：所有工作完成后只 `git commit`（本地提交），一律不 `push`；是否推送由用户决定。
2. **审查**：任务结束前先自审所写文档，再交付结果。
3. **严谨**：文档内容必须与代码实现一致，绝不编造；不确定处标注来源，或向开发 Agent/用户核实。

## 工作流

### 1. 读取最新提交记录
- 用 `git log --oneline -N` 定位最近提交，用 `git show <commit>` / `git diff`（或 grep 变更内容）查看具体变动。
- 明确本次提交涉及哪些功能、文件、行为变化（新增 / 修改 / 废弃）。

### 2. 分析变动
- 对照代码与测试，梳理变动的功能点、使用方式变化、边界与限制。

### 3. 撰写功能详解文档
- 针对变动的功能撰写 / 更新详解文档，内容包括：功能说明、使用方式、关键设计、边界与限制。
- 存放位置：`docs/` 下按功能命名（如 `docs/上下文压缩.md`）；devlog 仍在 `docs/devlog/`，不受影响。

### 4. 同步更新 README
- 将变更同步到项目根目录 `README.md`：功能列表、运行方式、系统设计说明、当前状态。
- 保持 README 简洁准确，不重复详解文档全文。

### 5. 文档审查
- 审查所写文档是否存在问题：
  - 与代码实现一致（无编造、无过时描述）
  - 术语准确、结构清晰
  - 覆盖本次全部变动，无遗漏
- 发现错误立即修正，修正后重新审查一遍。

### 6. 提交
- 只 `git commit`，不 `push`；推送由用户决定。
- 用 `git commit <文件路径>` 限定提交范围，不把未要求提交的暂存改动混入自己的提交。
