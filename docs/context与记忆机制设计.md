# context 与记忆机制设计（讨论记录）

> 记录时间：2026-11-05（P0 ①③ 提交后，②④⑥ 开工前）
> 状态：设计讨论稿，未实现。今天 P0 保持纯裁剪，摘要压缩 + 长期记忆并入 ⑦ 一起做。

## 一、背景

讨论来源：用户在消化自研 agent-harness 底层的 context 策略时，对比 Mitta 的记忆处理机制，产出了对"短期记忆窗口 + 摘要压缩 + 长期记忆召回"的完整想法。本文档原话保留用户方案，并附当前实现基线（防止遗忘）与后续待办。

## 二、当前实现基线（P0 ①③ 已提交，测试全绿）

**现状：纯窗口截断，无 LLM 压缩。** 对应需求文档"context 压缩：窗口截断 or summary 节点，后续判断取舍"中的"窗口截断"半。

- **裁剪条件**：按**估算 token 数**（`estimate_tokens` = `len//2` 粗算：中文≈1字1token、英文≈4字符1token），上限 `max_context_tokens=4000`。到顶才裁，没到不裁。不是轮数窗口。
- **异步**：`trim_messages` 是同步纯函数（无 IO）。裁剪本身不需要异步；将来加"LLM 摘要压缩"那一步才是异步（要调 LLM）。
- **被裁的旧消息去向**：**直接抛弃**。内存列表丢弃，`session.messages` 写回时也只留裁剪后的（system 被过滤，只存 `session.system_prompt` 字段）。**目前没有任何归档——这是与长期记忆的衔接缺口**。
- **传给模型的上下文**：`system + 保留的最近消息`。没有"被压缩上下文 + 裁剪后上下文"双通道。

## 三、用户方案（原话整理）

### 3.1 时间注入 system prompt

当前时间注入 system prompt 是**很有必要的**——真实 LLM 无内置时钟，不注入的话 agent 很容易读错时间。

### 3.2 理想记忆处理机制（参考 Mitta）

1. **裁剪 + 压缩双通道**：把旧的上下文裁剪掉，并且把被裁剪掉的上下文交给 LLM 压缩，然后跟着裁剪后的那 N 个 token 一起作为上下文。
2. **窗口不膨胀**：每次裁剪后，上下文窗口并不会膨胀——到了 max token 就进行裁剪并压缩。压缩处理需要**一致保持一定窗口大小**，否则会膨胀。
3. **长期记忆兜底**：每轮对话触发长期记忆处理并落库；LLM 每轮根据 **10 条 message 上下文 + 10 条语义上下文**压缩处理。后续即便每次短期记忆处理触发压缩导致某些不重要的信息被裁剪，也可以通过长期记忆进行召回。

### 3.3 工具列表处理

- **全量拼没问题**：目前工具数量少，工具列表全量拼入 system prompt 零成本，语义召回工具当前需求不大。
- **Mitta 的处理策略（参考）**：已有工具是白盒，可以直接获取工具上下文；存在 MCP 里的黑盒工具，Mitta 用"闪连"——先拿到工具三个字段，放进语义库做检索，再按需连接 MCP 以及工具调用。

### 3.4 项目收益认知

Mitta 的很多架构、策略都能直接拿现成（BM25 检索、乘法衰减、记忆召回时机与放置方式等），这是这个项目带来的最大收益。

## 四、待办建议（防遗忘清单）

### 4.1 摘要压缩（summary 节点）——并入 ⑦

- 裁剪时把被裁掉的旧消息调 LLM 压成一段摘要，作为"历史摘要"消息插在 system 之后。
- OpenAI 兼容协议没有 summary role，惯例塞进 system 或消息列表最前。
- 传给模型的结构：`system + 历史摘要 + 最近 N 条`。
- **防膨胀**：摘要本身必须计入 token 预算（如摘要上限 500 token）。
- **触发频率控制**：压缩有成本（LLM 延迟 + token 费），每 N 轮或达阈值才压，不能每轮都压。

### 4.2 长期记忆——⑦（照搬 Mitta）

- BM25 检索 + 乘法衰减（Mitta 设计直接 copy）。
- 存储用 SQLite：**复用已落地的 `SessionStore` 抽象**（sessions/messages/traces 表已就位，logs 表留给中间件）。
- 每轮 QA 落库 + 每轮检索 top-k 拼入上下文（用户方案：10 条 message 上下文 + 10 条语义上下文）。
- 短期窗口裁掉的信息，长期记忆可召回——闭环。

### 4.3 落地节奏

- **今天 P0 保持纯裁剪不动**（已提交全绿，MVP 合格，即"窗口截断"那半）。
- **摘要压缩 + 长期记忆合并到 ⑦ 一起做**（同属 context/记忆域）。

### 4.4 工具语义召回——暂缓

- 工具上量之后才需要（当前个位数，全量拼零成本）。
- Mitta 的闪连方案（先拿工具三字段 → 语义库检索 → 按需连接）作为工具规模化后的参考。
