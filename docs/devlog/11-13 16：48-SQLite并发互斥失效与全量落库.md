# SQLite 模式并发互斥失效与全量落库

## 现象

会话的「忙保护」在 `SESSION_STORE=memory` 下表现正常（第二条消息返回 409），但切到 `SESSION_STORE=sqlite` 后，同一条会话的两条消息可以同时进入主循环：两条都返回 200，刷新会话后少一条回复。同时每次 `save()` 都对该会话的 messages/traces 做 DELETE + 全量 INSERT，会话越长写库越慢。

## 根因

**一、互斥建立在对象内存字段上，而 SQLite 模式没有共享对象。**

`async_run` 原本靠 `session.state` 判断：

```
if session.state != "idle": raise SessionBusyError
session.state = "busy"
```

内存实现下 `SessionManager.get()` 返回字典里的同一个对象，单事件循环内「判断 + 赋值」之间没有 await 点，天然原子。

SQLite 实现下 `SQLiteSessionStore.get()` 每次从三张表**重建一个新的 Session 对象**，而 `state` 只在 `save()` 时才 `UPDATE sessions SET state = ?`。于是：

```
请求 A: get() → 新对象A（state 读库=idle）→ 设 busy（仅对象A 内存）→ 跑 LLM/工具……
        整个请求周期内，库里 state 恒为 idle
请求 B: get() → 新对象B（state 读库=idle）→ 同样放行 → 也进入主循环
```

两个实例各自跑完、各自 `save()`，后写者的 messages 全量覆盖先写者，导致一轮回复丢失。窗口不是毫秒级竞态，而是**整个请求时长**——用户秒发、双端同开、前端重试都能命中。

**二、落库时机晚于对外可见。**

`manager.save(s)` 在 endpoint 里 `await runtime.async_run(...)` 返回之后执行，而第二轮请求的 `get()` 从库里读——若它在第一轮的 save 之前到达，读到的历史缺少上一轮回复。

**三、save 是全量重建。**

`DELETE FROM messages WHERE session_id=?` + `executemany` 全量插入，成本 O(会话总长)，每轮都付一次。

## 修复

1. **互斥下沉到存储层**：`SessionStore` 新增 `try_acquire(session_id) -> bool` / `release(session_id)`。
   - SQLite：`UPDATE sessions SET state='busy' WHERE session_id=? AND state='idle'`，`rowcount == 1` 才算抢到；`rowcount == 0` 再查存在性区分「忙（返回 False）」与「不存在（抛 SessionNotFoundError）」。
   - 内存：`threading.Lock` 内判断 `state` 再置 busy，语义对齐。
2. **写回后立刻落库**：`AgentRuntime` 新增可选 `sessions: SessionStore` 依赖，在 `session.messages` 写回、`traces` 追加之后立即 `save()`，再释放会话。注入后互斥与落库都走存储层；未注入时保留原有内存路径，既有调用方与测试零影响。
3. **增量落库**：`save()` 先查 `COUNT(*)`，只插入 `session.messages[n:]` / `session.traces[m:]`。前提是二者只追加不裁剪（`trim_messages` 只作用于发给 LLM 的副本，不回写 session）。副作用是上一轮落库失败时，下一轮会按行数差自动补上。
4. **finally 只兜异常**：正常路径 `release()` 后紧跟 `released = True`（中间无 await），`finally` 只在 `not released` 时释放，避免异常兜底把下一轮刚抢到的持有权误放掉。
5. `main.py` 移除 endpoint 收尾的全量 `manager.save(s)`（已由 runtime 增量完成）。

## 验证

- `LLM_BACKEND=mock SESSION_STORE=memory LOG_STORE=memory pytest tests -q` → **185 passed**（新增 10 个用例）。
- 新增用例覆盖：SQLite CAS 抢占互斥 / 未知会话抛 NotFound / release 幂等 / 增量 save 只追加不翻倍 / 内存实现同等语义 / runtime 注入 store 后正常释放 / busy 拒绝 / 异常逃逸后释放 / 写回后立刻可从另一实例读到回复。

## 遗留

- `manager.save` 已移入 runtime（同步调用），SQLite 模式下仍会阻塞事件循环；当前增量后成本很低，暂不改为 `to_thread`。
- 多 worker 部署仍不成立：`SessionManager._sessions`、`InMemoryQueue` 都是进程内结构，需 `--workers 1`。跨进程方案是把互斥/历史/事件队列全部换成共享存储（PG / Redis），不属于本次范围。
