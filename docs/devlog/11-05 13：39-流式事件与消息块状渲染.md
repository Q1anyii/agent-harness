## 背景

- 需求文档要求流式输出 + trace 嵌入 AI 消息（参考 Mitta）。
- 用户明确：用内存队列解耦（Mitta 当初用 Redis，本笔试项目不上 Redis，但保持抽象可换）；前端 1s 级 setInterval 轮询；断连后先全量刷新消息再续拉增量。

## 实现（后端）

1. **EventQueue 抽象 + InMemoryQueue**（`src/agent/events.py` 新建）
   - 抽象方法：publish / subscribe / latest_seq / clear（实现可换内存 → Redis Stream，无需改 runtime）。
   - 内存实现：每会话一个 deque（保留最近 500 条）+ 单调 seq + threading.Lock。
   - publish 自动附加 seq；subscribe(since) 返回 seq > since 的增量。

2. **事件协议**（type 字段，每条带 seq）：
   - `reasoning{content}`：LLM 思考过程（⑥ 数据来源）
   - `tool_call{id,name,args}`：决定调用工具（② 工具子组件前半）
   - `tool_result{id,name,result,status,duration_ms}`：工具执行完（② 与 tool_call 按 id 配对）
   - `message_delta{delta,done}`：最终回复增量块（④ 流式传输载体）

3. **LLM 层**（`src/agent/llm.py`）：LLMResponse 新增 `reasoning` 字段；
   DeepSeek 读取 `reasoning_content`；MockLLM 两条路径返回演示 reasoning（测试确定性）。

4. **Runtime 事件推送**（`src/agent/runtime.py`）：`__init__` 加 `queue: EventQueue | None = None`
   （不传静默跳过，既有 sync 测试零影响）；run/async_run 循环内推送全部事件；
   最终回复 `_chunk_text(size=24)` 切块 + `_publish_reply`（最后一块 done=True）。

5. **API**（`src/main.py`）：全局 `InMemoryQueue()`；`GET /api/sessions/{sid}/events?since=N`
   （未知会话 404，返回 `{session_id, events, latest_seq}`）；delete_session 时 clear 事件。
   POST /messages 同步契约保留不变——前端先 POST 拿最终结果，同时轮询渲染增量。

## 实现（前端）

1. **types.ts**：ChatMessage 扩展 `tool_calls` / `tool_call_id`；新增 StreamEvent / ToolCallBlock / AiBlock。
2. **api.ts**：新增 `getEvents(sid, since)`。
3. **App.tsx**：`streaming` 状态（当前流式 AI 块）+ 1s 级 setInterval 轮询（seqRef 锚点）；
   send = 挂空 AI 块 → 启动轮询 → POST → 刷新全量消息 → 停轮询；
   POST 404（后端已失效）→ 自动新建会话；轮询失败静默下轮重试（断连恢复靠全量刷新兜底）。
4. **ChatBox.tsx**：块状消息盒子——扁平 messages 聚合成 RenderItem：
   user（右）独立；assistant(tool_calls) 与其后 tool 结果按 tool_call_id 配对成一个 AI 块。
5. **AiMessageBox.tsx**（新组件）：思考过程（`<details>` 折叠）+ 工具子组件列表 + 回复文本；
   streaming 时前端打字机动画（纯视觉，真实逐 token 流后续可换 LLM stream 接口）。
6. **ToolCallCard.tsx**（新组件）：单个工具卡片（名称/参数/结果/耗时/状态）。
7. **styles.css**：`.msg-body/.reasoning-box/.tool-card*/.ai-content/.ai-thinking` 等样式。
