# 架构设计题：

### **模块一：Context / Performance**

**1.大模型面对第一轮长窗口或多模态输入时，first token 会显著变慢。有什么快速/低成本/用户体验也不差的方案？从5-10秒稳定压缩到2秒。**

**2.一个 session 连续聊了 200 轮，context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？**

我觉得比较好的记忆处理机制，就是设置max_token,把旧的上下文裁剪掉，并且把被裁剪掉的上下文交给llm压缩，然后跟着裁剪后的那n个token一起作为上下文，这样的话每次裁剪后，它的上下文窗口并不会膨胀，等于是到了maxtoken，进行裁剪并压缩，当然这个压缩处理是需要一致保持一定窗口大小的，否则会膨胀，那么也由此引出长期记忆，每轮对话触发长期记忆处理并落库，然后llm每轮根据10条message上下文和10条语义上下文压缩处理。后续即便每次短期记忆处理触发压缩导致某些不重要的信息被裁剪，那么也可以通过长期记忆进行召回.

### **模块三：Task**

**1.对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？**

**2.用户给 Agent 下达任务：每天早上 9 点根据昨天聊天情况做复盘总结。你会怎么设计？**

这个任务其实是我现在每天都在用的，从我自身作为用户的角度出发来看：先制定一个定时任务，给出具体的提示词，然后选定时间，并点击执行。后续每天都会按时触发任务。

从设计者角度来看：我本身并没有接触过python定时自动脚本，不过我之前写Java项目的时候用过shchedule注解，那么这样的话其实就可以以此设置一个脚本，主要参数包含：执行时间、用户需求。LLM在调用工具前，将触发时间解析为icorn格式。另外的话其实还需要做时间隔离，这方面其实就可以像prompt处理一样，服务端传入local-datetime，做隔离，另外的话还可以用一个IO API，用文件整理，防止记忆混乱。不过这个工具并不能脱离user而存在，所以直接将其作为一次客户端sendMessage接口比较合适。
